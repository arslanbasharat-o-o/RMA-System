# v0.4.1: faster verified-library recognition

This release keeps the v0.4.0 decision policy and its high-detail final
comparison unchanged. It removes the main latency cost in the reference stage:
v0.4.0 searched the verified library in two sequential rounds of eight-model
batches and then ran a third high-detail comparison.

## What changed

- **One compact discovery pass.** With up to 32 verified device models, the
  engine now shortlists the whole library in a single discovery call. Larger
  libraries still use bounded batches, but every batch in a round runs
  concurrently (default concurrency **2**, configurable with
  `OPENAI_CONCURRENCY`).
- **Cheaper discovery inputs.** Discovery sends each reference's focused
  sensor/notch view at high detail plus a low-detail context frame, uses
  `reasoning_effort: low`, and requests only the selected catalog ID and
  confidence. The final comparison keeps the v0.4.0 high-detail frames, full cue
  schema, `reasoning_effort: medium`, and 8,000-token budget.
- **No repeated image preparation.** Sharp frames and focused crops are cached
  per image buffer, so discovery and the final comparison do not reprocess the
  same photos.
- **Stage timings in the audit record.** `recognition_runs.raw_response.timings`
  records discovery, final, and total milliseconds for each comparison.
- **Human review unchanged.** No confidence threshold, acceptance rule, or item
  status changed. The final comparison remains the only stage whose output can
  influence the applied suggestion, and the operator still confirms the model.

## Verification

Frozen 12-model holdout, production database read-only, with the source item and
every target checksum excluded from the reference set:

- **12/12 exact model accuracy (100%)**
- **9/12 accepted (75.0%)**
- **100% accepted precision**
- **12/12 review suggestions (100%)**
- **100% review-suggestion precision**
- **0 false confident matches**
- **0 errors**
- p50 benchmark case latency (Lens + comparison): **39.1 s**
- p95 benchmark case latency: **52.8 s**
- p50 comparison stage (discovery + final): **28.0 s**
- p95 comparison stage: **37.9 s**
- p50 discovery **12.3 s**, p50 final **13.9 s**

The v0.4.0 frozen holdout measured p50 **77.6 s** and p95 **93.4 s** for the same
12 cases. The p50 case latency therefore fell by **49.6%** and p95 by **43.5%**.

The acceptance and suggestion coverage improved from v0.4.0 (7/12 accepted,
10/12 suggested) without changing thresholds, the final comparison, or the
review policy. The improvement comes from the discovery shortlist feeding a
more relevant set of finalists to the same high-detail comparison. All nine
acceptances satisfy the existing corroboration rules. The three correct models
that remain without an accepted suggestion are iPhone 15 (0.96, one reference,
just below the decisive 0.97 rule), iPhone 16 Pro (0.91, one reference with an
unresolved alternative), and iPhone 16 Pro Max 120 Hz (0.96, one reference with
an unresolved alternative); each is still shown as a review-only suggestion.
Exact-model accuracy, accepted precision, and review-suggestion precision all
remained at 100%, with no false confident match.

Non-database unit tests: **190/190 passed**. Seven database-backed tests that
require a local PostgreSQL instance were not run in this workspace. TypeScript
and ESLint pass; the production build is validated during deployment. The live
production replay after deployment must show the supplied iPhone XR in review
before this release is considered verified.
