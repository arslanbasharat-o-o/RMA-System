# v0.4.0: model-level verified recognition

This is the single consolidated recognition release after v0.3.34. It supersedes
the v0.3.34 candidate, which was built but never deployed. The focus is the
engine, not another one-image exception: verified references are now counted per
device model, and a reference-backed model remains visible to the operator even
when the comparison is not strong enough to accept automatically.

## What changed

- **Model-level corroboration.** Verified items are grouped by device model, not
  by catalog SKU. The two verified iPhone XR assemblies (`AM` and `COF`) now
  count as two independent XR references. The shortlist prefers the exact SKU
  proposed by search when it has a verified photo, and otherwise uses a verified
  sibling assembly of the same model.
- **Honest acceptance policy.** A comparison is applied at **0.93** confidence
  only when it has at least two model-level references, or one reference plus
  independent search agreement, or a decisive single-reference match (at least
  **0.97**, at least three concrete cues, no unresolved alternative). Two
  references may outweigh a residual caveat the comparison already considered.
- **Review-only suggestions.** When a reference-backed comparison selects a
  model but does not meet the acceptance policy, the model is shown as a review
  suggestion instead of leaving the display unidentified. The item is forced to
  `review_required`; the suggestion is never auto-verified. Thresholds are 0.85
  for one reference without an unresolved alternative, 0.90 for one reference
  with an unresolved alternative, and 0.80 for two or more model-level
  references, with at least two matching cues.
- **Actionable review.** A concrete reference-backed suggestion can be approved
  in one action even when the synthesized status is ambiguous. Items with no
  concrete model and catalog ID remain blocked.
- **Audit trail.** Recognition runs record the model-level reference count,
  candidate IDs, reference item IDs, discovery batches, cues, and unresolved
  alternatives.
- **Evaluation tooling.** The read-only feedback benchmark now reports
  review-suggestion coverage and precision in addition to exact-model accuracy,
  accepted coverage/precision, false confident matches, errors, and latency.

## Verification

Frozen 12-model holdout, production database read-only, with the source item and
every target checksum excluded from the reference set:

- **12/12 exact model accuracy (100%)**
- **7/12 accepted suggestions (58.3%)**
- **100% accepted precision**
- **0 false confident matches**
- **0 errors**
- **10/12 review suggestions (83.3%)**
- **100% review-suggestion precision**
- p50 comparison latency: **77.6 s**; p95: **93.4 s**

The frozen holdout covers iPhone 15 Pro Max, iPhone 11, iPhone 11 Pro Max,
iPhone 12 Pro Max, iPhone 13 Pro Max, iPhone 14 Pro, iPhone 14 Pro Max, iPhone
15, iPhone 16 Pro, iPhone 16 Pro Max 120 Hz, iPhone 16 Pro Max, and iPhone XR.
The main run produced 11/12 exact model accuracy because the provider returned a
transient `500` on the iPhone 15 Pro Max case. That single case was rerun with the
final build (which retries one transient 5xx) and returned iPhone 15 Pro Max at
`0.96` with two model-level references. The merged result is the 12/12 above; the
retry is recorded rather than hidden. The two correct models that remain without
a review suggestion are iPhone 16 Pro (`0.89`, one reference, one unresolved
alternative) and iPhone 16 Pro Max (`0.77`, two references, one unresolved
alternative); the conservative policy intentionally abstains there.
The previous baseline scored 8/12 exact model accuracy and 2/12 accepted
coverage at 100% accepted precision.

Non-database unit tests: **189/189 passed**. TypeScript, ESLint, and the
production build pass. The live production replay after deployment must show
the supplied iPhone XR in review before this release is considered verified.

## Live replay

Deployed to `https://rma.txparts.io` as v0.4.0 and replayed against the supplied
iPhone XR photo on both a temporary smoke-test item and the original review
item. Both replays returned:

- **Apple iPhone XR** (`Apple iPhone XR (COF LCD)`)
- confidence **0.98**
- **2 model-level verified references** (the XR `AM` and `COF` assemblies)
- no unresolved alternatives
- `review_required`, not verified

The recognition run is `openai-verified-examples:gpt-6.1-sol`, and the item
remains unverified for the operator. A one-click `accept_suggestion` was also
exercised on the temporary item; it correctly moved that item to
`manually_verified`. The temporary RMA, customer, item, review action, storage
directory, queue rows, and admin session were then deleted. The original item
was left `review_required` with no review actions and no verification timestamp.

## Limitations

The verified library is intentionally sparse: 32 active catalog SKUs covering 26
device models, against 2,443 active catalog rows and 1,739 distinct model names.
A model without a verified reference cannot receive a reference-backed
confirmation. Photo-only comparison also cannot separate physically identical
variants when the photo lacks distinguishing evidence (for example 120 Hz versus
non-120 Hz panels); those cases remain `review_required` with explicit
unresolved alternatives. This is retrieval-time example learning, not
model-weight fine-tuning.

## Deployment

Deployed directly to production outside GitHub CI/CD at the user's request. The
version is bumped once for the completed engine release; no per-change version
churn. The latest known-good database and storage backup is retained as the
rollback safety net.
