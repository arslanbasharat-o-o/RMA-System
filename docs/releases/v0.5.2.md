# RMA System v0.5.2 — Visual Decision Policy Invalidation & Reasoning Model Token Hardening

Release Date: 2026-10-31
Target Infrastructure: Production KVM2 VPS (`rma.txparts.io`)
Runtime: Node.js 24 / Next.js 16 / PostgreSQL 16 / Docker Compose

## Executive Summary

Release `v0.5.2` addresses two critical production recognition defects discovered during live server validation on ambiguous displays:

1. **Policy Invalidation & Stale Snapshot Purge**: Bumped `VISUAL_DECISION_POLICY` to `source-corroboration-2026-10-31-v8`. Under the previous policy (`v7`), scans of previously uploaded images were reusing pre-v0.5.0 snapshots from the database where historical buggy heuristics had stored incorrect models (such as `iPhone 8 Plus` for an `iPhone 13` image). Bumping the policy enforces re-evaluation of images using the hardened v0.5.1+ multi-candidate consensus engine.
2. **Reasoning Model Completion Token Budget**: Increased `max_completion_tokens` from 350 to 2048 in `cleanVisualCandidatesWithOpenAi`. When using reasoning models (such as `gpt-5.6-terra`), reasoning tokens count against `max_completion_tokens`. A 350-token limit exhausted all tokens during internal thinking, returning empty message content and causing JSON parse failures (`"Malformed cleaner response"`). Expanding to 2048 tokens provides ample headroom for reasoning and JSON payload output.
3. **Upstream Suggestion Preservation**: Ensured that when visual cleaner response is malformed, abstained, or encounters provider errors, the upstream Google Lens consensus suggestion (`evidence.suggestedModel`, e.g. `iPhone 13`) is retained for operator review rather than prematurely wiped to `"Unidentified Display"`.
4. **Forced Retry Cache Override**: Ensured that when `options.force` is active on re-runs, fresh recognition results always take precedence over historical database snapshots regardless of whether the fresh model is provisional or definitive.
